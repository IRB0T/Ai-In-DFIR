DFIR-IBHA – Internet Browsing History Analyzer

MODE: COGNITIVE CHAT (Claude.ai / Gemini Advanced / Any Chat LLM)

WHAT THIS FILE IS

This is the Cognitive Chat version of DFIR-IBHA.

Use this file when: - You are working inside Claude.ai (Pro or free) -
You are using Gemini Advanced without code execution - You are using
ChatGPT without the Data Analysis tool enabled - You are using any other
LLM chat interface where you can upload files but cannot execute code

In this mode, you – the LLM – read the CSV file directly from the
conversation context and perform the analysis by scanning rows manually.
No Python is executed. All analysis is done cognitively.

Other versions: - DFIR-IBHA-CodeInterpreter.md – ChatGPT Plus with Data
Analysis (runs Python) - DFIR-IBHA-Agentic.md – CoCo, Cursor, Claude
Code (full IDE with file tools)

## MODEL-SPECIFIC TIPS & CONTEXT LIMITS

Different LLMs handle large CSV files differently. Read the section for your
platform before uploading your file.

---

### Claude.ai (claude.ai/chat or Claude Projects)

**Context window:** ~180,000 tokens usable ≈ 25,000–35,000 CSV rows

**Strengths:** Best in class for cognitive chain detection. Excellent narrative
writing. Follows structured scanning instructions very reliably.

**Tips:**
- Use Claude Projects (claude.ai/projects) and paste this skill file as the
  Project Instruction. Then every conversation in that project auto-loads the
  skill – you only need to upload the CSV and send the command.
- Claude reads the CSV carefully but can miss rows if the file is very wide
  (many columns). Pre-trim your export to: `url, title, visit_time, visit_count`
  only. This roughly doubles the row count that fits in context.
- Add to your command: `"After completing the scan, confirm how many rows
  you read in total."` – Claude will comply and this tells you if the file
  was truncated.
- If you get a partial analysis, export a date-filtered CSV (e.g., 30-day
  window) and re-run.

### Universal Tips (All Models)

## CONFIDENCE CALIBRATION

**READ THIS SECTION CAREFULLY.**

Because this analysis is done by reading rows in context — not by executing code — honesty about what you did and did not see is critical. Forensic reports that assert findings without proper qualification create legal risk and can mislead investigations.

You MUST follow these rules in every DFIR-IBHA analysis:

---

### Rule 1 — Count and Report Rows Read

After completing the scan, include this block in the report:

```
SCAN COMPLETENESS STATEMENT
____________________________

Total rows in file (visible) : [N]
Rows within date filter       : [X]
Rows actually scanned         : [Y]
Context window status         : SUFFICIENT / NEAR LIMIT / EXCEEDED
Completeness                  : FULL SCAN / PARTIAL SCAN — [reason]

If PARTIAL: "Results may be incomplete. Recommend re-running with a
date-filtered export covering [suggested range] only."
```

If you could not read the entire file, say so explicitly and quantify what you could read. Do not produce a report that implies full coverage when the file was truncated.

### Rule 2 — Three Confidence Levels, Used Consistently

**CONFIRMED:** You directly observed the URL and/or page title clearly matching the IOC indicator.
- Example: URL is `https://mega.nz/folder/abcDEF#xyz`, title is "Shared Folder – MEGA"
- You saw both the domain AND contextual signals. Use this for direct matches.

**PROBABLE:** The URL domain matched the watchlist but the title was empty, truncated, or not meaningful.
- Example: URL is `https://wetransfer.com/transfers/upload`, title is blank
- The domain match is clear but you cannot confirm the action from the title.

**POSSIBLE:** The domain looks similar to a watchlist entry but you are not certain. Single visit could be a corporate variant or a coincidental match.
- Example: URL is `https://upload.companyname.com` — superficially similar to an exfil service but likely internal
- Flag it, note the ambiguity, recommend human review.

Never assign CONFIRMED to a POSSIBLE-level match to strengthen a report. A POSSIBLE finding that is later confirmed by other evidence is still useful. A false CONFIRMED finding can invalidate an investigation.

---

### Rule 3 — Never Extrapolate or Estimate

Do not say: "There were likely more visits to this site outside the visible rows."
Do say: "X visits to this site were observed within the rows I scanned."

Do not say: "The pattern suggests the subject frequently uses file transfer sites."
Do say: "Within the scanned rows, [N] visits to file transfer services were observed across [X] unique domains between [date] and [date]."

If your count is approximate because the file was large, say so:
"Approximately [N] visits observed — exact count may vary if the file was truncated."

### Rule 4 — Ambiguous URL Handling

If a URL is partially cut off, garbled, or unclear:
- Record it as: `URL: [partial — visible portion: xxxx]`
- Confidence: POSSIBLE
- Do not try to complete or guess the missing parts.

If a domain looks similar to a watchlist entry but is not an exact match:
- Note: `"Domain [observed] is similar to watchlist entry [expected] but may be a corporate intranet or CDN variant. Flag for human review."`
- Confidence: POSSIBLE

---

### Rule 5 — Citation Format

Every finding must follow this citation format:

```
URL            : [exact URL or domain if NSFW]
Title          : [exact title as it appeared] or [not available]
Timestamp      : [exactly as it appeared in the data]
Visit count    : [number] or [not available]
Row position  : approximately row [N] in the file
Confidence     : CONFIRMED / PROBABLE / POSSIBLE
```

If any field was missing from the original data, write `[not available]` — never substitute a guess or leave the field blank.

### Rule 6 — The Scan Completeness Statement

Every DFIR-IBHA cognitive report must end with this statement before the appendices:

```
ANALYST SCAN COMPLETENESS STATEMENT
____________________________________

This analysis was performed by cognitive row scanning (no code execution).

Rows visible in this session : [N]
Date filter applied           : [DATE_FROM] to [DATE_TO]
Rows within scope             : [X]
Full file scanned             : [YES / NO — if no, explain]

All findings are based solely on rows visible in this analysis session.
This report should not be treated as exhaustive if the row count visible
is significantly less than the total rows in the source file.

Recommendation: Cross-validate HIGH and CRITICAL findings using the
CodeInterpreter or Agentic version of DFIR-IBHA on the complete dataset
before using this report as the sole basis for any action.
```

**Why this matters:**

In a real investigation, the difference between CONFIRMED and POSSIBLE can determine whether a finding is admissible in a disciplinary hearing. A DFIR report that over-claims confidence is worse than one that under-claims — over-claiming can expose the organization to legal challenge, undermine the case, or result in wrongful action against an innocent subject.

When in doubt, mark it POSSIBLE and recommend follow-up. That is not
weakness — that is professional forensic practice.
